# gian-new — Eazotel core API

The **single backend** for Eazotel: the dashboard (web), the **Android app**, hotel websites, booking engines and the onboarding app all talk to it, and nothing else. **TypeScript, class based, one self-contained folder per module, shipped as a Docker image.**
It replaces both of today's backends, module by module, until neither nexon nor gian has to run:

## 0. What we are building

1. **Self-onboarding creates everything.** A hotel fills the onboarding form. A background job then builds, step by step and retryably:
   - the account and property;
   - a full **booking engine** (rooms, weekday/weekend prices, taxes, an 18-month calendar);
   - room photos on **S3 + CloudFront**;
   - the website **content + SEO generated by AI**;
   - a **GitHub repo named after the property** (`amaltas`), created from our Next.js + Tailwind site template;
   - a **Vercel project** that deploys it.

   → [docs/PLATFORM-FLOW.md](docs/PLATFORM-FLOW.md) §1–3
2. **Professional booking engine**, like the Booking.com extranet:
   - per-day prices, availability and restrictions;
   - default weekday and weekend prices, single-day edits and bulk edits (date range + chosen weekdays), with a clear rule for which price wins;
   - extra-guest pricing, promotions and GST slabs per night;
   - signed quotes, atomic inventory holds (no overbooking), Razorpay per property, cancellation policies.

   → [docs/BOOKING-ENGINE.md](docs/BOOKING-ENGINE.md)
3. **New CMS in the dashboard**:
   - the hotelier types a prompt ("change the hero to monsoon offers") → AI edits only the content → before/after diff → save draft (preview URL) → publish (commit to the site repo → Vercel redeploys);
   - also manual editing, images, and SEO (meta title, description, keywords, OG, sitemap, JSON-LD);
   - versions with one-click rollback.

   → [docs/PLATFORM-FLOW.md](docs/PLATFORM-FLOW.md) §4
4. **Images:** room images live in S3 behind CloudFront, because the booking engine and the site both need them (cheap, cached for a year). Other images (hero, gallery…) are committed to the site repo's `public/images`, and can also be added by hand.
5. **One lead hook for every site.** It posts to gian-new with a site key, so leads are always saved under the right property. Old sites posting to nexon `/eazotel/addcontacts` keep working.
6. **Analytics and SEO, rebuilt.**
   - **One Google connection per property**, covering Analytics 4, Search Console, Tag Manager, Business Profile and Ads.
   - Data is synced daily into our own snapshots, so dashboards are fast and keep history.
   - Pages: Overview with a combined funnel (search → visits → bookings → revenue, plus leads), Website traffic (page views, users, sources, events, booking funnel, realtime), Search (queries, CTR opportunities, indexing), Local (Business Profile visibility, calls, directions, reviews, NAP check), SEO health (on-page audit, Core Web Vitals, rank tracking, geo-grid), Tags (GTM health) and Ads.

   → [docs/ANALYTICS-SEO.md](docs/ANALYTICS-SEO.md)
7. **Nothing breaks.** Old sites, booking engines and the dashboard keep calling nexon until each endpoint is moved, tested and switched at nginx, one at a time (§9).

## 1. Principles

1. **A module is a folder that owns everything about its feature**: routes, controllers, services, repositories, models, DTOs, middlewares, config/env, types, events, jobs and tests. To understand or delete a feature you open one folder (§3).
2. **Class based and layered.** `Routes → Controller → Service → Repository → Model`. Each class has one job (§2).
3. **Dependency injection.** Classes receive their dependencies in the constructor. Each module wires its own classes in `<module>.module.ts`. The root `container.ts` only creates the modules in order and passes each one what it needs from the others. No `new SomeService()` inside another class.
4. **Modules talk only through public APIs.** A module may import another module's `index.ts` and nothing deeper. ESLint enforces this (§3.4).
5. **Validate at every edge with zod.** That covers request DTOs, response DTOs (never return raw DB documents), each module's env, and every response from a third party or from nexon.
6. **Config is read in one place per module.** Only `config/*.config.ts` files read `process.env`. The app refuses to start with bad config.
7. **Never break a running client.** Every nexon URL that a dashboard, booking engine or hotel website calls keeps working, with the same path and the same response shape, until we decide to retire it (§9).
8. **Secure by default.** Every route needs auth unless it is marked public. The tenant (`ndid`/`hid`) comes from the token and is never trusted from the body.
9. **Same artifact everywhere.** One Docker image runs in dev, staging and production. Only env changes.

## 2. SOLID in this codebase

| Principle | Meaning here |
|---|---|
| **S**ingle responsibility | Controller = HTTP only. Service = business rules. Repository = DB queries for one collection/aggregate. Client = one external API. |
| **O**pen/closed | A new payment gateway or login method is a new class implementing `PaymentGateway` / `LoginStrategy`, not another `if (type === "x")`. |
| **L**iskov substitution | Any `PaymentGateway` (Razorpay, a fake in tests) can replace another without the service changing. |
| **I**nterface segregation | Small ports (`BookingReader`, `BookingWriter`, `EngineDetailsSource`) instead of one huge service that everything depends on. |
| **D**ependency inversion | Services depend on interfaces. The module file decides the concrete class: native, nexon-backed, or a test fake. |

File naming: `<name>.<role>.ts` in kebab-case everywhere (also `shared/` and the top-level `app.ts`, `server.ts`), one class per file, the class named in PascalCase after the file (`refresh-token.repository.ts` → `RefreshTokenRepository`). Tests use Node's built-in runner (`node:test` + `node:assert`) with in-memory fakes of the ports, see `modules/auth/__tests__/`. A big module may split into sub-features that each follow the same skeleton, e.g. `booking-engine/{rooms,rates,inventory,bookings,payments,promo-codes}/`.

### 3.3 How a module plugs in

```ts
// shared/module/AppModule.ts
export interface AppModule {
  readonly name: string;
  readonly router?: Router;          // mounted at /api/v1 (strict CORS, cookies)
  readonly rootRouter?: Router;      // mounted at / for /health/*, /.well-known/*
  readonly legacyRouter?: Router;    // mounted at / (old nexon paths, open CORS like nexon)
  init?(): Promise<void>;            // e.g. build the indexes of the module's own collections
  registerJobs?(queues: QueueFactory): void;   // when queues land
  shutdown?(): Promise<void>;
}

// modules/auth/auth.module.ts
export class AuthModule implements AppModule {
  readonly name = "auth";
  readonly router: Router;
  readonly legacyRouter: Router;
  readonly authenticate: AuthenticateMiddleware;   // public: other modules protect their routes with it
  readonly tokens: TokenService;                   // public: e.g. HMS verifies via JWKS, users module issues invites

  constructor(deps: { config: AuthConfig; logger: Logger; events: EventBus; users: UsersPort }) {
    const credentials = new CredentialRepository();
    const refreshTokens = new RefreshTokenRepository();
    this.tokens = new TokenService(deps.config);
    const service = new AuthService(credentials, refreshTokens, this.tokens, deps.users, [
      new PasswordStrategy(credentials, new PasswordService()),
      new GoogleStrategy(deps.config.google),
      new LegacyTokenStrategy(deps.config),        // old nexon logins keep working during migration
    ], deps.events);
    const controller = new AuthController(service);
    this.authenticate = new AuthenticateMiddleware(this.tokens);
    this.router = new AuthRoutes(controller, this.authenticate).router;
    this.legacyRouter = new AuthLegacyRoutes(controller).router;
  }
}

// container.ts (root): builds infra, then modules in order. Nothing else.
const auth = new AuthModule({ config: authConfig, logger, events, users: usersModule.port });
const properties = new PropertiesModule({ config: propertiesConfig, auth: auth.authenticate, logger });
export const modules: AppModule[] = [health, auth, usersModule, properties /* … */];
```

### 3.4 Module boundary rules (lint-enforced)

- `modules/a/**` may import `modules/b/index.ts` only (rule `no-restricted-imports`, or `dependency-cruiser` in CI).
- `shared/` and `integrations/` never import from `modules/`.
- No circular module dependencies. If two modules need each other, one side gets a port (interface) or an event.
- Each module owns its collections. Another module reads them through that module's public service, never through its model.
- Imports use Node subpath aliases from `package.json` `"imports"`: `#shared/*`, `#modules/*`, `#integrations/*`, `#config/*`. These work with `module: nodenext` and need no bundler.

### 3.5 Request flow

```text
HTTP ─► request-id ─► logger ─► Routes ─► authenticate ─► requirePermission ─► validate(Dto)
     ─► Controller ─► Service ─► Repository ─► MongoDB
                           └──► integrations (Razorpay, WhatsApp, Google…) — responses zod-validated
errors anywhere ─► error-handler ─► { success:false, error:{ code, message, details, requestId } }
```

### 3.6 Example: the shape to copy

```ts
// modules/booking-engine/bookings/dtos/create-booking.dto.ts
export class CreateBookingDto extends BaseDto {
  static schema = z.object({
    hid: z.string().min(1),
    roomTypeId: z.string().min(1),
    checkIn: z.coerce.date(),
    checkOut: z.coerce.date(),
    guests: z.number().int().min(1).max(20),
    guest: z.object({ name: z.string().min(1).max(100), phone: z.string().min(6).max(20), email: z.email().optional() }),
  }).refine((b) => b.checkOut > b.checkIn, { message: "checkOut must be after checkIn", path: ["checkOut"] });
}
export type CreateBookingInput = z.infer<typeof CreateBookingDto.schema>;

// services/booking.service.ts
export class BookingService {
  constructor(
    private readonly bookings: BookingRepository,
    private readonly inventory: InventoryPort,
    private readonly payments: PaymentGateway,       // interface: Razorpay today, anything tomorrow
  ) {}

  async create(ndid: string, input: CreateBookingInput) {
    await this.inventory.hold(ndid, input.hid, input.roomTypeId, input.checkIn, input.checkOut);
    const booking = await this.bookings.create({ ndid, ...input, status: "pending_payment" });
    const order = await this.payments.createOrder({ amount: booking.total, reference: booking.id });
    return { booking, order };
  }
}

// controllers/booking.controller.ts — BaseController auto-binds methods, so routes need no .bind()
export class BookingController extends BaseController {
  constructor(private readonly service: BookingService) { super(); }

  async create(req: Request, res: Response) {
    const result = await this.service.create(req.auth.ndid, req.body as CreateBookingInput);
    return this.created(res, BookingResponseDto.from(result));
  }
}

// routes/booking.routes.ts
export class BookingRoutes extends BaseRoutes {
  constructor(c: BookingController, auth: AuthenticateMiddleware) {
    super("/bookings");
    this.router.post("/", auth.require("booking:create"), validate.body(CreateBookingDto), c.create);
  }
}
```

A working JavaScript version of `BaseController` (auto-bound methods), `BaseDto`, the validation middleware, `Container` and `Server` already exists in `HMSBackend/src`. Port it to TypeScript as the first thing in `shared/`.

## 4. Configuration & env

- **Global** config (`src/config/`) covers what every module needs: `NODE_ENV`, `PORT`, `LOG_LEVEL`, `MONGO_URI`, `MONGO_DB` (= `Courage`), `REDIS_URL`, `CORS_ORIGINS`.
- **Module** config (`modules/<m>/config/<m>.config.ts`): each module validates **its own prefixed vars** and receives the typed result in its constructor. For example `AUTH_JWT_PRIVATE_KEY`, `AUTH_ACCESS_TTL=15m`, `BOOKING_HOLD_TTL_MIN=15`, `RAZORPAY_KEY_ID`, `WEBSITE_PUBLISH_BUCKET`.
- **Integration** config sits next to its client (`integrations/razorpay/razorpay.config.ts` → `RAZORPAY_KEY_ID`).
- `config/env.ts` runs every schema at boot and prints *all* missing or invalid variables in one message, then exits. No module reads `process.env` directly.
- `.env.example` has one section per module, in the same order as `container.ts`, and lists every variable from every schema. A CI check fails if a schema key is missing from it.
- `.env` and `.env.*` (except `.env.example`) are never committed. In Docker, env comes from `env_file`/the host. On AWS it comes from SSM Parameter Store / Secrets Manager.

```ts
// modules/auth/config/auth.config.ts
const schema = z.object({
  AUTH_JWT_PRIVATE_KEY: z.string().min(1),
  AUTH_JWT_ISSUER: z.string().default("https://api.eazotel.com"),
  AUTH_ACCESS_TTL: z.string().default("15m"),
  AUTH_REFRESH_TTL_DAYS: z.coerce.number().int().positive().default(30),
  AUTH_GOOGLE_CLIENT_ID: z.string().min(1),
});
export type AuthConfig = Readonly<z.infer<typeof schema>>;
export const loadAuthConfig = (env: NodeJS.ProcessEnv): AuthConfig => Object.freeze(schema.parse(env));
```

How it is wired (implemented):

- `config/config-section.ts`: `ConfigSection(name, zodSchema)`. Every global, module and integration config is one section.
- `config/env.ts`: `Env.loadFile()` reads `.env` (host variables win, skipped when `NODE_ENV=test`). `Env.validate(sections)` checks all sections, then throws one `EnvValidationError` that lists every problem. `KEY=` (empty) counts as not set, so defaults apply.
- `config/env.schemas.ts`: shared parsers (`csv`, `flag`, `duration`, `mongoUri`, …).
- `config/index.ts`: `configSections` (the one list, in container order) and `loadConfig()` → typed, frozen `Config`.
- `npm run env:check` (`scripts/check-env-example.ts`) fails when `.env.example` and the schemas drift.
- `NODE_ENV` (development | test | production) controls library behaviour. `APP_ENV` (development | staging | production) names the deployment. Staging runs with `NODE_ENV=production`.
- The JWT key is the RS256 PEM, base64-encoded on one line (the generate command is in `.env.example`). The public key and JWKS are derived from it.

Environments: `development` (local Docker), `staging` (test phase; uses a **copy** of the database, never production `Courage`), `production`.

## 6. API conventions

- New endpoints: `/api/v1/<resource>`, plural nouns. `GET` list/read, `POST` create, `PATCH` partial update, `DELETE`.
- Old nexon endpoints keep their **exact** old path, method and response (§9), including typos such as `/booking/availablity` and `/eazotel/ceateuser`.
- Success: `{ "success": true, "data": ..., "meta": { "page": 1, "limit": 20, "total": 134 } }`
- Error: `{ "success": false, "error": { "code": "BOOKING_DATES_UNAVAILABLE", "message": "…", "details": [{ "field": "checkIn", "message": "…" }], "requestId": "…" } }`
- Status codes: 400 validation, 401 no/invalid token, 403 no permission, 404, 409 conflict, 422 business rule, 429 rate limit, 502 upstream (nexon/third party) failed, 500.
- Pagination: `?page=&limit=` (max 100), or a cursor for feeds. Always sort explicitly.
- Dates: ISO 8601 UTC. The property's time zone is stored on the property.
- Money: integer minor units (paise) + currency code. Never floats. Legacy mappers convert to the old format when needed.
- Idempotency: `Idempotency-Key` header on booking and payment creation.
- Every response carries `X-Request-Id`, and every log line includes it.
- Health: `GET /health/live` (process is up) and `GET /health/ready` (Mongo reachable). Docker and the load balancer use these.

### 6.1 API docs (Swagger), generated

- **`/docs`**: Swagger UI. Log in with `POST /api/v1/auth/login` ("Try it out"), copy `data.accessToken`, press **Authorize**, paste it, and every protected route can be tried. **`/docs/openapi.json`**: the raw spec.
- On by default everywhere except `APP_ENV=production` (`API_DOCS_ENABLED` overrides).
- `npm run docs:export` writes `docs/openapi.json` without a server or DB: import it into Postman, generate the Android app's Kotlin client (`openapi-generator-cli generate -g kotlin -i docs/openapi.json`), or diff it in a PR.
- **Nobody writes docs by hand.** A route is declared once, with its spec, and that one declaration gives Express the route, the request validation and the docs:

  ```ts
  // modules/<m>/routes/<m>.routes.ts
  this.post(
    "/:hid/rooms",
    {
      summary: "Create a room type",
      params: HidParamsDto,             // validated + documented
      body: CreateRoomDto,              // validated + documented (field .meta({ description, example }) shows in Swagger)
      response: { status: 201, schema: roomResponseSchema },   // zod schema of `data`
      errors: { 409: "ROOM_CODE_TAKEN" },                      // stable error codes of this route
    },
    auth.require("bookingEngine", { hid: (req) => req.params.hid }),   // → bearer + 401/403 in the docs, automatically
    c.create,
  );
  ```

  Middlewares document themselves: `auth.require()` adds the bearer lock, 401/403 and the permission; rate limiters add 429. Tags come from the routes class (`super("/rooms", { tag: "Rooms" })`). Old nexon paths use `envelope: false, validate: false, deprecated: true` and appear under "Legacy (nexon)".

### 6.2 Logging

- Development (`LOG_FORMAT=pretty`, the default there): one coloured line per request, errors as a readable block with the stack:

  ```text
  [13:17:43.439] INFO: POST /api/v1/auth/login 200 124ms  req 4b811d90
  [13:17:43.532] INFO: GET /api/v1/auth/me 200 5ms  user 6ae990b9  req 38b267c9
  [13:17:43.668] WARN: POST /api/v1/auth/login 401 76ms  req dc352b18
  [13:17:48.315] ERROR: POST /api/v1/auth/login 500 connect ECONNREFUSED 127.0.0.1:27017  req b832fb75
      err: { type, message, stack (with every "caused by") }
  ```

- Staging / production (`json`): the same events as one JSON object per line (`requestId`, `req.method`, `req.url`, `res.statusCode`, `responseTime`, `userId`, `err`) for CloudWatch queries.
- Levels: 2xx/3xx info, 4xx warn, 5xx error. `/health` and `/docs` are not logged. A failing request is **one** entry (the error handler hands the error to the access log).
- `requestId` is the `X-Request-Id` response header and is in every error body: search the logs for it.
- Never logged: `Authorization`, cookies, passwords, tokens (pino `redact`). Errors are trimmed to type, message, code and stack (drivers attach huge objects, e.g. MongoDB's topology).
- In code: `logger.info({ ndid, hid }, "booking created")`. Fields go in the object, never glued into the message. Never `console.log`.

### 6.3 Fast responses (rules for every endpoint)

The dashboard feels slow when an endpoint does more work than its answer needs. In 2026-11, the old gian `GET /api/v1/leads/get` showed every item below. It loaded **all** of a hotel's Facebook leads (full documents) on every call, just to list campaign names. It sorted by a date computed for every lead. It ran the count only after the page query. And the Leads page called it **6 times** (the list plus 5 stage counters). Don't port that shape. Build every endpoint like this:

#### Reading data

- **Fetch only what the response returns.** Use a projection, never whole documents "just in case". For a list of values use `distinct()` or a `$group`, never `find().toArray()` and a loop in Node.
- **Filter first, then compute.** The first `$match` uses indexed fields (`ndid`, `hid`, `status`, `source`, dates). `$addFields`, `$lookup` and regex search come after it, on as few documents as possible.
- **Sort on a stored, indexed field.** If records need a "sort date", compute it **when the record is written** and store it. Never compute it in the pipeline for every document on every read.
- **An index for every query.** Declare it in the model (§13) in the order equality → sort → range, e.g. `{ ndid: 1, hid: 1, status: 1, sortDate: -1 }`. Check the query with `.explain("executionStats")` and look for `IXSCAN`. `docsExamined` should be close to `nReturned`.
- **Paginate everything.** Default limit 20, max 100 (§6). Exports stream a cursor instead of building one huge array.
- **Text search on a large collection** uses an anchored regex (`^term`) on an indexed field, or a text/search index. An unanchored `$regex` over 11 fields scans everything.

#### Doing the work

- **Independent queries run in parallel.** The page and its total run together: `Promise.all([find, countDocuments])` or one `$facet`, never one after the other.
- **One request for one screen element.** Counters, badges and stat cards get one endpoint that returns all the counts with a single `$group` (e.g. `GET /leads/stats` → `{ Open: 12, Contacted: 4, ... }`). Never one request per number.
- **Return everything a screen needs at once.** If the client must make call A before call B (e.g. "is calling connected?" before "list calls"), return both in one response or let B answer the "not connected" case itself.
- **No third-party calls inside a request.** Exotel, Meta, Google and WhatsApp are slow and rate-limited. Sync them into Mongo with a queue job or cron, and let endpoints read Mongo. If a live call is unavoidable, give it a timeout and cache the result.
- **Auth costs no database lookup per request.** The access token carries what the guard needs (user, ndid, permissions, §7). Anything that still has to be loaded (e.g. a legacy token's ndid) is cached in memory for a few minutes, keyed by user. The old gian looked up `Zucks_users` on every call.
- **Keep heavy work out of the request.** Emails, push, WhatsApp, PDFs and imports go to a queue job. The endpoint answers `202` with a job id.

#### Responses

- **Keep the payload small.** Lists return list fields only. The detail endpoint returns the full record. Turn on `compression`. Never return the internal fields of a nexon or third-party response.
- **Send cache headers where it's safe.** Use `Cache-Control: private, max-age=…` for data that rarely changes (properties, team, settings, templates), so the dashboard and app can reuse it.

#### Checking it

- **Budget:** list and detail endpoints answer in **under 300 ms** on production data (p95). Anything slower needs a reason in the PR.
- **Measure, don't guess.** The access log has `responseTime` per request (§6.2). Filter CloudWatch for slow ones (`responseTime > 500`) and fix the top offenders first. Set `MONGO_SLOW_MS` (mongoose debug in development) to see slow queries while building.
- **Test with real volume.** Seed a test hotel with **10,000+ leads and calls** before calling an endpoint done. Every endpoint looks fast on 20 documents.

#### Client side (dashboard and Android app)

- Cache responses and reuse them: RTK Query `keepUnusedDataFor` of a few minutes, refetch in the background, and show the old data while new data loads. Never blank the screen on a revisit.
- Don't make one request per row or per counter. Ask the backend for a combined endpoint instead.

#### Hosting

- Production must not sleep. A host that idles instances out (e.g. a free plan) makes the first request after a quiet period take 30–60 s. Run at least one always-on instance, with `/health/live` as the health check.

## 7. Authentication & tenancy (gian-new becomes the identity provider)

**Implemented (2026-11-03)**: endpoints, token formats, the password rules during the migration and every class are in [src/modules/auth/README.md](src/modules/auth/README.md). Reasoning: `HMSBackend/docs/LOGIN-DESIGN.md`. Summary:

- `modules/auth` issues **RS256** access tokens (15 min) plus rotating refresh tokens (httpOnly cookie for browsers, JSON body for the Android/iOS app via `X-Client-Platform`), and publishes its keys at `/.well-known/jwks.json`.
- **Staff** are not hotel users. They live in `admin_users` and sign in to the admin console through `modules/admin` (Google + an emailed 6-digit code, token audience `eazotel-admin`, cookie `ez_admin_rt`, invite only). A staff member opens a client's dashboard with `POST /api/v1/admin/clients/:ndid/open-account`, which checks their permission and assigned properties, logs it, and returns a 1-hour hotel token. This replaced the earlier email-domain staff rule and `/api/v1/auth/switch-account` (2026-11-05); gian-new's copy of nexon's `/admin/switch-account` always answers 403. See [src/modules/admin/README.md](src/modules/admin/README.md). HMS and the booking-engine widgets verify tokens with the public key.
- Login methods are strategies: email + password, Google, phone OTP (WhatsApp/SMS), and **legacy token**. nexon signs its logins with an HS256 secret (gian's `JWT_SECRET`). The legacy strategy verifies those tokens locally with `AUTH_LEGACY_JWT_SECRET`, so a user already logged in through nexon is accepted and old sessions don't break, without any call to nexon. It is removed once every client uses the new login.
- Token claims: `sub`, `sid` (session), `ndid`, `email`, `role`, `admin`, `perms[]` (account `accessScope` flags), `props: [{ hid, perms[] }]` (`assigned_location`), `iss`, `aud`, `exp`. Permission names are today's `accessScope` keys (`cms`, `bookingEngine`…), so no data migration is needed.
- The legacy secret is also used to **sign** nexon-style tokens on the old login paths gian-new serves, so a login answered by gian-new still works against nexon and gian.
- `modules/users` holds team members and roles → permissions per property. It replaces the access list in the dashboard's User Management.
- `authenticate.require("perm")` runs on every route. Services receive `ndid`/`hid` from `req.auth`, never from the body.
- Guest tokens (GRM, booking engine "manage my booking") are a separate short-lived token type.

### 9.2 Strategy: strangler behind nexon's own nginx

Old clients include booking engines embedded on hotel websites, the dashboard, the onboarding app and the chatbot. They call `https://nexon.eazotel.com/<path>` and some have the URL hard-coded, so we **don't make clients change URLs**. Instead, the nginx that already fronts nexon sends migrated paths to gian-new and everything else to Flask:

```nginx
# /etc/nginx/sites-enabled/nexon  (excerpt)
upstream nexon_flask { server 127.0.0.1:5000; }     # existing
upstream gian_new    { server 127.0.0.1:8000; }     # gian-new container (or its internal ALB/host)

# one location per migrated endpoint; removing the block = instant rollback
location = /booking/availablity             { proxy_pass http://gian_new; include proxy_params; }
location ^~ /booking/getenginedetails/      { proxy_pass http://gian_new; include proxy_params; }

location /                                  { proxy_pass http://nexon_flask; include proxy_params; }
```

New clients (and new dashboard screens) call `/api/v1/*` on gian-new directly (e.g. `api.eazotel.com`). Old and new clients work side by side, and nothing needs a coordinated release.

### 9.3 Phases

| Phase | What happens | Clients notice? |
|---|---|---|
| **A. Build & test** | gian-new runs on staging (copy of DB). The dashboard's `VITE_CORE_API_URL` stays on nexon. New features use `/api/v1` on gian-new. | no |
| **B. Port natively** | gian-new never calls nexon. Each feature is rewritten in its module and reads/writes the shared `Courage` collections directly. Until a path is cut over, nginx keeps sending it to nexon, so nothing waits on gian-new. | no |
| **C. Legacy routes + shadow** | The legacy route answers with `<module>.legacy.mapper.ts` in the exact old shape. Golden tests (9.4) pass. Optionally mirror real traffic (nginx `mirror`) and diff the responses without serving them. | no |
| **D. Cut over per endpoint** | Add the nginx `location` for that path → gian-new. Watch error rate and latency. To roll back, delete the block and `nginx -s reload`. | no |
| **E. Retire** | When every path of a module is on gian-new for 2+ weeks with no rollback, delete that code from nexon. When nothing is left, `nexon.eazotel.com` points straight to gian-new. | no |

Rules: one endpoint at a time; writes (bookings, payments) move only after their reads are stable; no DB schema change while nexon still reads that collection.

### 9.4 Contract safety net

gian-new has no nexon client and no `NEXON_*` config: nexon is only ever reached by nginx (9.2), never by gian-new. The two systems meet in the shared database, which is why collections keep their field names and shapes until nexon is retired.

### 9.6 Security holes in the running nexon (found 2026-11-03, `main` @ `9ee9bf98`)

These are live in production now. gian-new does not have them, but they stay open until nexon is fixed or the path is switched in nginx. Fix order:

| # | Where | Problem | Impact | Quick fix in nexon |
|---|---|---|---|---|
| 1 | `POST /admin/switch-account` | signs **any JSON body** as a token, with no auth check (`utils.create(data)`) | anyone can get a valid token for **any hotel account** (`{"Email": "<owner>"}`) | **gian-new answers it with 403** (staff use the admin console's Open account instead): add the nginx `location` for this path. Or block it in nginx |
| 2 | `POST /admin/login` | issues a token even when the password is wrong (the `find_one` result is never checked) | anyone gets an admin token for any admin email | `if admin is None: return False` |
| 3 | `POST /feature1/otp-verify` | the OTP check result is ignored; a token is issued for any OTP | anyone can read and cancel any guest's bookings by phone number | return False when `verifyOtpToNumber` fails |
| 4 | `POST /user/delete/<email>` | no authentication at all | anyone can delete any dashboard user | require the owner's token, same ndid |
| 5 | `POST /eazotel/forgot/password` | replaces the password immediately and emails a new one | anyone can lock any user out (the password changes on every call) | send a reset link with a one-time token instead |
| 6 | `settings.py`, `local.py`, `.env`, `nexon.py` | JWT secret, Mongo URL, Razorpay secret, OpenAI key and Google client secret are **committed to git** | anyone with repo access can mint tokens and read the database | rotate every secret, move them to env/SSM, remove them from git |

| 8 | Google sign-up | every account created with Google starts with the password `Eazotel@123` | password login into a Google-created account that hasn't changed it | **Kept on purpose** (owner's decision, 2026-11-06): hotels use it and can change it after logging in. gian-new does the same. ## 10. Docker

One image, two processes (API and worker), with the same code and different commands.

### 10.1 `Dockerfile` (multi-stage)

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-alpine AS base
WORKDIR /app

# all deps (incl. dev) for building and for local dev
FROM base AS deps
COPY package.json package-lock.json ./
RUN npm ci --include=dev

# compile TS, then drop dev deps
FROM deps AS build
COPY tsconfig.json tsconfig.build.json ./
COPY src ./src
RUN npm run build && npm prune --omit=dev

# small runtime: no compiler, no dev deps, non-root
FROM base AS runtime
ENV NODE_ENV=production
RUN apk add --no-cache tini
COPY --from=build --chown=node:node /app/package.json ./
COPY --from=build --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/dist ./dist
USER node
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=5s --start-period=20s --retries=3 \
  CMD wget -qO- http://127.0.0.1:8000/health/live || exit 1
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["node", "dist/main.js"]
```

`tini` forwards `SIGTERM` so `Server.ts` can finish in-flight requests and jobs before exiting.

### 10.2 `docker-compose.yml` (local development)

The real file is [docker-compose.yml](docker-compose.yml). It runs three containers: `api` on port 8000, `mongo` and `redis`.

| Command | What it does |
|---|---|
| `docker compose up --build -d` | Build and start everything in the background |
| `docker compose ps` | Show what is running and whether it is healthy |
| `docker compose logs -f api` | Follow the API logs (Ctrl+C stops following, not the API) |
| `docker compose down` | Stop everything and keep the data |
| `docker compose down -v` | Stop everything and **erase** the Docker database |

- Docker Desktop must be running first. Stop any `npm run dev` too, because both use port 8000.
- Edits in `src/` restart the API. After changing `.env` run `docker compose up -d`, and after changing `package.json` run `docker compose up --build -d`.
- Mongo is on port **27018** on the PC, because a MongoDB installed on Windows uses 27017. Compass: `mongodb://localhost:27018/?directConnection=true`. This database starts empty and is separate from the Windows one.
- Compose uses `npx tsx watch` rather than `npm run dev`, because `node --watch-path` does not work on Linux. `CHOKIDAR_USEPOLLING` is needed because Windows file changes do not reach Linux containers as events.
- Add a `worker` service when `src/worker.ts` exists.

`docker-compose.prod.yml` uses the `runtime` image (built in CI, pushed to **AWS ECR**, tagged with the git SHA), sets `restart: unless-stopped`, has no bind mounts, no local Mongo (Atlas/managed) and the env from the host. The first deploy target is an EC2 host next to nexon (so the nginx cutover in §9.2 is a local `proxy_pass`). Moving to ECS later needs no code change.

| Newer features are self-contained modules (`modules/whatsapp/templates/{controllers,dtos,models,repositories,services,types,schemas,client}`) | It is half-migrated: global `src/controllers`, `src/models`, `src/repositories`, `src/services` still sit next to `src/modules`. gian-new has **only** modules + `shared` |
| Ports with swappable implementations (`queue-port` → bull / in-memory, `file-store` → local / S3) | Routes create controllers with `new` and wire them with `.bind()`. Here modules wire classes and `BaseController` auto-binds |
| Module-local env (`contacts/import/config/import-env.ts`) and a state machine for long jobs | A single global `container.ts` exporting every singleton. Here each module has its own `*.module.ts` |
| Separate worker entry points | `console.log` in repositories and `any` filters. Here: pino logger, typed filters |
| `.env.example` documents defaults | Committed `logs/` and `bk.zip`. Ad-hoc `*.check.ts` scripts instead of a test runner. No Docker |
